# AI 利用記録 (ch04/ex03)

利用 AI: Claude Code (Claude Fable 5)
日付: 2026-09-20

解答コード (add / neg / sub) は自分で実装した。AI には考え方のヒント・デバッグの助言・JS の仕様確認のみを依頼した。

## 質問した内容と得られたヒント

### 1. ビット演算の前提

- 質問: JS では数値を 2 進数に明示的に変換してからビット演算する必要があるか？
- 回答: 不要。ビット演算子はオペランドを自動的に 32 ビット整数として解釈する (ToInt32)。`toString(2)` は表示用にすぎない。

### 2. `+` を使わない足し算の考え方

- 質問: `+` 禁止の中でどう足し算するか？ 繰り上がり時にシフトを使うのか？
- 回答 (ヒント): 半加算器の考え方。`a ^ b` が繰り上がりを無視した和、`(a & b) << 1` が繰り上がり。繰り上がりが 0 になるまで繰り返す。補数作成自体にはシフトは不要 (`~` と加算のみ)。
- また、`add` を先に作れば「~b に 1 を足す」(neg) も「a + (-b)」(sub) もすべて `add` の再利用で書けることを確認した。

### 3. `^` 演算子の確認

- 質問: `^` は XOR か？
- 回答: XOR (排他的論理和)。べき乗は `**` であり混同しないこと。

### 4. add のデバッグ (結果が -4 になるバグ)

- 症状: `add(3, 1)` が `-4` を返した。
- AI の指摘: ループ内で繰り上がり (`a & b`) を再計算しておらず、初回の繰り上がりをシフトし続けていたため、32 ビットから溢れるまでループが止まらなかった。各周で「新しい仮の和 (XOR)」と「新しい繰り上がり (AND + シフト)」の両方を、更新前の値を使って計算し直す必要がある。
- 修正は自分で実施 (一時変数に退避して更新順序の問題を回避)。

### 5. 桁溢れの扱い

- 質問: 補数や加算で 32 ビット目に溢れた先頭の 1 を消す処理は必要か？
- 回答: 不要。JS のビット演算は常に 32 ビットで動作し、溢れたビットは自動的に捨てられる (`(1 << 31) << 1 === 0`)。これにより繰り上がりが溢れると 0 になり、ループが自然に終了する。

### 6. 2 進数表示・リテラルの仕様確認 (デバッグ用)

- 32 ビットのビット列を確認する定番: `(n >>> 0).toString(2).padStart(32, "0")`
- 負の数の `toString(2)` は「マイナス記号 + 絶対値の 2 進表記」を返すため、ビット並びを見るには `>>> 0` が必須 (符号なし 32 ビットとして再解釈)。`>>` (2 つ) では符号が保たれるので不可。
- ビット演算の結果は「32 ビットのビット列」として保存されるのではなく普通の数値に戻る。`neg(5)` の結果は `5 - 10` の `-5` と同じただの数値。
- `0b` プレフィックスは 2 進数リテラル。ただし常に正の値を作るだけで、2 の補数として解釈されない (`0b111...1` (32 個) は `-1` ではなく `4294967295`)。

### 7. neg の動作確認

- 質問: `neg(-1)` が `1` になるのはおかしいのでは？
- 回答: 正しい。`neg` は符号反転なので `neg(-1) === 1`。負の数の補数を取れば正に戻る (`neg(neg(n)) === n`)。
- 併せて、モジュール直下の動作確認コード (`neg(-1);`) は import のたびに実行されるので削除を推奨された。

### 8. sub の組み立て方の確認

- 質問: `sub(8, 3)` では `neg` に `-3` ではなく `3` を渡す？
- 回答: その通り。`sub(a, b) = add(a, neg(b))` で、符号反転は `neg` の仕事。`b` が負の場合 (`sub(8, -3) === 11`) も自動的に正しく動く。

### 9. テストの失敗原因 (型の不一致)

- 症状: `expect((neg(1) >>> 0).toString(2)).toBe(0b111...1)` が失敗。
- AI の指摘: 左辺は文字列、右辺は数値で型が不一致。数値同士・文字列同士に揃えるか、いちばん素直な `expect(neg(1)).toBe(-1)` の形にする。

## 質問したプロンプトと得られた回答の要約

1. **「問題 6.8 で template オブジェクトにないプロパティを target から削除する関数を作成したけど、テストが 1 個も通らなかった」**
   - テストを実行してもらうと、restrict の 10 件すべてが `expected undefined to be {}` で失敗していた。失敗箇所はテストの 53 行目 `expect(result).toBe(target)`。
   - `Received: undefined` は、関数の戻り値が `undefined` だったという意味。
   - 問題文の「返値」の項目と、自分の関数が最後に何を返しているかを見比べるよう助言された。`return` がない関数は何を返すかを考えるヒントも出された。
   - `Object.keys` と `Object.hasOwn(template, key)` を使った削除の判定は問題に合っている。`Object.keys` は Symbol キーも継承プロパティも含まないので、「Symbol と継承プロパティは削除しない」条件も満たせている。直すのは 1 か所だけ。
   - テストが `toEqual` ではなく `toBe` を使っているのは、新しいオブジェクトを作って返すのではなく、受け取った `target` そのものを書き換えて返す必要があるため。

2. **「substract は restrict の複数対応版って考えてもいい？」**
   - 半分だけ合っている。複数のオブジェクトを受け取る点は同じだが、判定が逆。restrict は template に「ない」プロパティを消し、substract は sources に「ある」プロパティを消す。同じ `{ a: {} }` を渡しても、restrict では `a` が残り、substract では `a` が消えることをテストケースで比べて示された。
   - sources が複数のときは、どれか 1 つの source にでもあるプロパティを消す (テストの 111〜114 行目)。
   - ループの組み方は「target のキーを回して、どれかの source にあるか調べる」か「各 source のキーを回して target から消す」の 2 通りがある。
   - source の継承プロパティは判定に使わないケース (96〜98 行目) と、source に Symbol があっても target の Symbol は残るケース (81〜83 行目) に注意するよう言われた。
   - restrict と同じく、最後に何を返すかも忘れないこと。

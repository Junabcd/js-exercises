# AI 利用記録 (問題 5.9)

- 日付: 2026-09-30
- 使用ツール: Claude Code (Fable 5)

## プロンプト 1 (エラー内容の扱いとテストの書き方)

> Json.parse()で例外が出た時にキャッチしてエラー内容をだすってあるけど、これは本来のJson.parseのエラーメッセージを出せばいいのか、catchで上書きしてしまっていいのか判断がつかない。また、本来のエラーメッセージの場合はテストコードでエラーメッセージをどう書けばいいのかわからない。
>
> Json.parse()が成功した場合もテストコードでどうしようと思ったが、こっちはjsonの形式をそのままログ出力してテストで一致するか調べるのか

### 回答の要約

- 問題文の `<エラー内容>` は catch したエラーをそのまま入れると読むのが自然で、自作メッセージで上書きする必要はない。`error` に Error オブジェクトを入れるか `e.message` (文字列) を入れるかは自分で選び、テストもそれに合わせる。
- `JSON.parse` のエラーメッセージ文言はエンジン (Node のバージョン) 依存なので、テストで固定文字列と完全一致させるのは脆い。代わりに `toBeInstanceOf(SyntaxError)` や「空でない文字列である」といった性質を検証する。
- 成功時はログ出力の目視比較ではなく `toEqual` で深い比較をする (`toBe` は参照比較なのでオブジェクトには不適)。

## プロンプト 2 (JSON.parse の戻り値の確認)

> Json.parseってそもそもsuccessってもの返さなくない？

### 回答の要約

- そのとおりで、`JSON.parse` は成功ならパース結果の値を返し、失敗なら `SyntaxError` を throw するだけ。
- `{success, data}` / `{success, error}` の形のオブジェクトは、これから書くラッパー関数が自分で組み立てて返すもの。throw する API を結果オブジェクト形式に包むのがこの課題 (try-catch の練習) の趣旨。

## プロンプト 3 (ログ出力にするのは意図から外れないか)

> エラーの時に{success:false,e.message}をログ出力させるは問題の意図とは外れない？外れないならこの書き方使用かと思っている。

### 回答の要約

- `error` に `e.message` を入れること自体は問題の解釈として妥当。
- ただし問題文は「〜を返す関数」なので、ログ出力ではなく return が関数の仕事。console.log しかしないと戻り値が undefined になり Vitest で検証できない。ログは関数の外で必要なら出す。
- `{success: false, e.message}` は構文としても無効 (ショートハンドは単独の識別子のみ)。`error:` とキー名を明示する必要がある。

## プロンプト 4 (catch(e) と e.message)

> catch(e)って書けばe.messageも使用できないんだっけ？

### 回答の要約

- `catch (e)` と書けば `e.message` は使える。`JSON.parse` が投げる `SyntaxError` は `Error` を継承しており `message` を持つ。
- 使えないのは `(e)` を省略した `catch {` 形式 (ES2019 以降の書き方) の場合。

## プロンプト 5 (JSON のキーの引用符とテストの期待値)

> parseJson('{"a": 1}'))って{"a":1}だから{ success: true, data: { a: 1 } }のaも"a"って書かなきゃいけないんじゃないんだっけ？

### 回答の要約

- JSON の文法ではキーの `"a"` は必須だが、パース結果は普通の JavaScript オブジェクトになる。
- JavaScript のオブジェクトリテラルでは識別子として有効なキーの引用符は省略可能で、`{ a: 1 }` と `{ "a": 1 }` は同じオブジェクト。テストの期待値は `data: { a: 1 }` で一致する。

## プロンプト 6 (テストコードでの error.message 参照)

> error.messageってテストコードに直接書いてもError時のメッセージプロパティ取れるんだっけ？

### 回答の要約

- 取れるかは関数が `error` に何を入れたか次第。Error オブジェクトを入れる設計なら `result.error.message` でたどれる。`e.message` (文字列) を入れる設計なら `result.error` 自体がメッセージで、`.message` は undefined になる。
- 関数側の設計とテスト側のたどり方は対になっている。

## プロンプト 7 (テスト側で e を参照できるか / 本物のメッセージとの比較)

> toEqual(e.message)みたいなことはできないよね？

### 回答の要約

- `e` は関数内の catch ブロックのスコープにしかない変数なので、テストコードから直接は参照できない (ReferenceError になる)。
- 本物のメッセージと比較したい場合は、テスト側でも同じ不正 JSON を try-catch 付きで `JSON.parse` して期待メッセージを取得してから比較する方法がある。同じ実行環境なら同じメッセージになるので、固定文字列と違い環境が変わっても壊れない。

## プロンプト 8 (「エラー内容である」ことの検証と一発 toEqual)

> {success: false, error: <エラー内容>} を返す関数を書くのであれば、エラーメッセージであるってことはテストした方がいいんじゃない？

> toEqual({success: false, error: error.message}で一発でテストするのは難しいか。結局テスト側でparseして失敗させるのって、関数に入れるのと同じだし…。

### 回答の要約

- 「本物のエラー内容が入っている」ことまで検証する方が関数の契約に忠実、という問題意識は正しい。検証の強さは (1) 期待メッセージを動的に取得して一致まで見る > (2) `SyntaxError` インスタンスであることを見る > (3) 空でない文字列であることだけ見る、の順。
- 期待メッセージを先に変数へ取れば `toEqual({ success: false, error: expectedMessage })` の 1 つの expect で比較できる。また Vitest の非対称マッチャー `expect.any(String)` / `expect.any(SyntaxError)` を `toEqual` の期待値に埋め込めば、準備なしの一発で形を検証できる。
- テスト側で `JSON.parse` して期待値を作るのは循環ではない。検証対象は `JSON.parse` の正しさではなくラッパーの詰め替えロジック (握りつぶしていないか、形が正しいか、メッセージを加工していないか) で、標準ライブラリは信頼できる道具として共有しているだけ。

# AI 利用記録 (ch07/ex01)

- 日付: 2026-11-02
- 使用 AI: Claude Code (Opus 5.5)
- 用途: 行列の加算・乗算の定義の確認、関数の分け方の相談、行列の妥当性チェック (`isValidateMatrix`) の考え方とチェック順の相談、`every` の使い方の確認、エラーの種類とメッセージの相談、2 次元配列の組み立て方 (`push`) の確認、乗算のループ構造のヒント、テストが失敗した原因の調査。解答コードは AI に生成させず、ヒントと小さな例をもとに自力で書いている。

## 質問したプロンプトと得られた回答の要約

1. **「行列の加算と乗算の関数を作成するけど、それぞれの行列って同じ行数、列数の者同士なんだっけ？それともそれぞれ個別に設定できるようにするべき？」**
   - 関数はどんなサイズの行列も受け取れるようにして、計算できる組み合わせかを関数の中でチェックする (課題文の「定義できないサイズならエラー」はそのため)。
   - 加算: A と B の行数・列数が両方同じであること。同じ位置の要素どうしを足す。
   - 乗算: A の列数 = B の行数であること。`A (m×n) × B (n×p) = C (m×p)`。C の i 行 j 列は「A の i 行目と B の j 列目の対応する要素の積の合計」。A×B と B×A は一般に別物。
   - テストに入れるとよいケース (正常系、サイズ不一致のエラー、行の長さがそろっていない配列など) と、Vitest の `expect(() => ...).toThrow()` を教わった。

2. **「これって加算用と乗算用に関数分けて書いた方がいいかな？」**
   - 分けるのがおすすめ。サイズの条件・計算方法・結果のサイズがすべて違う、`add(a, b)` のほうが呼び出し側が読みやすい、テストが書きやすい (単一責任の原則)。
   - 行列の形のチェックなど共通部分は補助関数に切り出してもよいが、最初から無理に共通化しなくてよい。

3. **「まず前提として引数に入ってきたやつで配列じゃないやつはエラーにしていいよね？」**
   - エラーにしてよい。途中でわかりにくいエラーや `NaN` が出るより、最初にはっきり止めたほうが親切。
   - チェック候補: 引数が配列か / 各行が配列か / 全行の長さがそろっているか / 要素が数値か / 空の配列をどう扱うか。
   - `Array.isArray()` (`typeof [] === "object"` なので `typeof` では判定できない)、`every`、`TypeError` と `RangeError` の使い分けを紹介された。

4. **「(各行が配列か / 全行の長さ / 要素が数値か / 空の配列) これらのヒントをください」**
   - 各行: `every` + `Array.isArray`。全行の長さ: 最初の行を基準に `every` で比べる (行が配列であることを確認した後に行う)。
   - 要素: `every` の中で `every`。`typeof x === "number"` は `NaN` / `Infinity` を通し、`Number.isFinite()` は弾く。
   - 空の配列: `[].every(...)` は常に `true` を返す落とし穴がある。`[]` のとき `m[0].length` はエラーになる。エラーにするか許すか方針を決めてテストで確認する。

5. **「m.every(x => Array.isArray(x)) で各要素が全部配列を持つか調べられるってこと？」**
   - その通り。`every` は先頭から順に調べ、1 回でも `false` ならそこで止まって `false` を返す。`for` で書いた場合との対応を教わった。
   - 似たメソッドに「1 つでも〜があるか」を調べる `some` がある。

6. **「every の中でもう一度 every って m.every(x => x.every(y => Number.isFinite(y))) みたいなのでいいの？」**
   - それでよい。ただし各行 `x` が配列であることが前提なので、行が配列かのチェックを先に通しておく必要がある (そうしないと `x.every is not a function`)。

7. **「空ではないかについては最後にチェックしても問題ない？あと、どこかに空があれば即 false にすることにした。つまり行も列も最低 1 は必要」**
   - `every` だけで書いていれば最後でも動くが、`every` の外で `m[0]` に触れた時点でエラーになるので、前のほうに置く (ガード節) のがおすすめ。
   - 「全行の長さがそろっているか」のチェックがあれば、空かどうかは `m.length` と `m[0].length` の 2 つを見れば十分。
   - チェック順の例: 配列か → 行数 1 以上 → 各行が配列か → 列数 1 以上 → 全行の長さ → 全要素が数値か。

8. **「このチェックでエラーを投げる場合は何がいいんだろう RangeError？TypeError？」**
   - 型が違うなら `TypeError`、形やサイズの問題なら `RangeError` か `Error` (どちらかに統一すればよい)。
   - Vitest で `toThrow(TypeError)` のように種類まで指定すると、自分のバグによる別のエラーに気づきやすい。

9. **「isValidMatrix で false が返ってきたらエラーにする場合は？」**
   - 理由が呼び出し側に伝わらないので、不正な行列はまとめて `TypeError` にするのがよい。サイズの不一致は別のチェックなので `RangeError` にすると区別できる。
   - 理由ごとにエラーを分けたい場合は、チェック関数自体がエラーを投げる形 (`assertMatrix` など) にする。

10. **「a は有効な行列ではありませんを英語に」「throw new RangeError("行列のサイズが一致しません") を英語で」**
    - `"a is not a valid matrix"`、`"Matrix sizes do not match"` などを教わった。テンプレートリテラルでサイズを入れる書き方も紹介された。

11. **「加算でサイズが違うをいよいよチェックするが、table1 と table2 がある場合は every を使えば for 文はいらない？」「サイズの違いを調べるのに for はいらないの？」**
    - `every` も `for` もいらない。`isValidateMatrix` を通った時点で形が確定しているので、行数 `table.length` と列数 `table[0].length` の 2 つの数字を比べるだけ。

12. **「逆に言えば、どちらかが false の場合は RangeError を投げればいいのか」**
    - その通り。`!(A && B)` と `!A || !B` は同じ (ド・モルガンの法則)。行数だけ違う・列数だけ違う・両方違う、の 3 パターンをテストするとよい。

13. **「計算結果の配列って最初に空で作成しておいて push するのがいいのか、for 文で table1 と同じものを作成した方がいいのか」**
    - table1 をコピーして上書きする方法には落とし穴がある。`const result = table1` や `[...table1]` (浅いコピー) では行が共有され、引数を書き換えてしまう (問題 7.5 の破壊的操作と同じ話)。乗算では結果のサイズが違うのでそもそも使えない。
    - 空の配列に `push` で組み立てるか、`map` で新しい配列を作るのがおすすめ。

14. **「push ではどう書けばいいんだろう。result[x][y].push でいいのか？あと空の 2 次元配列は [[]] で作れる？」「空の配列作るのに結局 for 文で一回回して全部作らなきゃいけない？いまだに 2 次元配列への push がわからん」「result[row].push(); だとまた微妙に違いが出るんだっけ？」**
    - `result[x][y]` は数値なので `push` は使えない。`[[]]` は空の行が 1 つあるだけ。
    - 先に空の配列を全部作る必要はない。行ごとに空の配列を作って値を `push` し、完成した行を結果に `push` する。2 次元配列に直接 push しているのではなく、1 次元の `push` を 2 種類しているだけ。`result` と `row` の中身の変化を 1 ステップずつ表で説明してもらった (行列とは別の例)。
    - `result.push([])` で先に空の行を入れておけば `result[i].push(値)` とも書ける。

15. **「足し算できたから、掛け算に移行する。このプロンプトで聞いた掛け算のヒントを書いて」**
    - 乗算の条件、結果のサイズ、各要素の計算方法、3 重ループの構造、結果の配列の組み立て方、エラーチェック、テストケースをまとめてもらった。

16. **「(ループの構造について) 考え方のヒントをください」**
    - 外側からではなく、結果の 1 マス (0 行 0 列) の計算から考える。`k` が増えると、A は同じ行のまま横に、B は同じ列のまま縦に進む。
    - 0 を `i`, `j` に置き換え、`j` のループで 1 行、`i` のループで全行を作る。合計の変数は `j` のループの中、`k` のループの外で 0 に初期化する。

17. **「result.push([]); でもかける？」**
    - 書ける。`i` 周目で push した行は必ず `result[i]` になる。`j` のループより前に書くこと。

18. **「あれ、add のテストなんでうまくいかないんだ？」**
    - AI にテストを実行してもらった。原因は 2 つ。
    - `isValidateMatrix` の `m.every(row => m[0].length === m[row].length)`: `every` の `row` はインデックスではなく行の配列そのものなので、`m[row]` が `undefined` になっていた。
    - テストの `toEqual([8,10,12],[14,16,18])`: 期待値は 2 次元配列 1 つにする必要がある。
    - 「全行の長さ」「全要素が数値か」のテストは、意図したチェックではなくこのバグの `TypeError` で通っていたことを指摘された。
    - `maltiple` のスペルミスと、乗算のループの回数も見直すよう言われた。

19. **「else if(!m.every(row => m[0].length === m[row].length)) なんでこれダメなの？」「m[0].length と row.length を比較すればいいのか」**
    - `for` 文の `row` はインデックスだが、`every` の `row` は要素。`m[[1, 2, 3]]` は `m["1,2,3"]` を探すので `undefined` になる。`console.log(row)` で中身を確かめるとよい。
    - `m[0].length` と `row.length` を比較すればよい。

20. **「掛け算のほうってループが間違ってるらしいけどなんでだ？あれ、回し方違う？」「28 行目は table[0] の長さを見ればよくて、30 行目は table2.length でいいってことね」**
    - 28 行目の `table2[row]` は、A の行数が B の行数より多いと存在しない行を見てエラーになる (3×2 × 2×3 など)。B の列数は `table2[0].length` で取る。
    - 30 行目の `k` は A の列数 (= B の行数) だけまわす必要があり、B の列数を使うと項が足りず黙って間違った答えになる (2×3 × 3×2 など)。`table2.length` でよい。
    - 正方行列ではこの取り違えに気づけないので、サイズの違う行列でテストする。

21. **「2x2 同士の行列の掛け算ってどうなるんだっけ？」**
    - 一般形と、`[[1,2],[3,4]] × [[5,6],[7,8]] = [[19,22],[43,50]]` の例、順番を入れ替えると結果が変わることを教わった。

22. **「なんか掛け算がうまくいかないけど、関数間違ってる？」**
    - AI にテストを実行してもらった。`multiply` 関数は正しく、テストで `add` を呼んでいたのが原因 (返ってきた値が足し算の結果だった)。
    - Received の値が何を計算した結果かを考えると原因を見つけやすいこと、2×3 × 3×2 などのケースと `multiply` の `TypeError` のテストを追加するとよいことを教わった。

# AI 利用記録 (ch03/ex13)

- 利用ツール: Claude Code (Fable 5)
- 日付: 2026-09-09
- 利用方針: 解答コードは書いてもらわず、アルゴリズムの考え方のヒント・仕様の確認・デバッグの相談のみ行った。実装は自力で行った (AI からはヘルパーの骨組みスケッチ・条件式の断片レベルのヒントのみ受領)。

## 相談内容 (プロンプトの要約) と得たヒント

### eq のアルゴリズム理解

1. **「出だしがわからない。== ならまず Number() で数値変換するように書けばいい?」**
   → 最初のステップは変換ではなく「両辺の型を調べること」。同じ型なら変換せず `===` で比較して終わり。型が違うときだけ変換ルールが登場する。eq 全体は 6 ステップ (①同じ型→`===` ②null と undefined のペア→true ③数値 vs 文字列→文字列を Number() して再帰 ④論理値→数値化して再帰 ⑤オブジェクト vs 数値/文字列→基本値化して再帰 ⑥それ以外→false) の平らなルール表になる、というヒントを得た。「変換した値で eq を再帰呼び出しする」のが最大のヒントだった。

2. **「『オブジェクトの場合』というのは null 以外の object のこと?」**
   → その通り。`typeof null` が `"object"` なのは歴史的なバグのようなもので、null は基本値。null は `undefined` とだけ `==` で true になり、それ以外 (0 や "" を含む) とは常に false。「typeof が object かつ null でない、または function」という isObject 条件が必要と教わった。

3. **「同じ型同士でも == なのに === を返していいの?」**
   → 型が同じとき `==` と `===` は完全に同じ動作をする (型変換は型が違うときだけ)。また eq の実装内で `==` 自体を使ったら再現にならないので、問題の条件で `===` が許可されている。

4. **「数値には Infinity とかあるよね?」**
   → Infinity/-Infinity/NaN/±0 はどれも typeof が "number" で、`===` の挙動が `==` と一致するため特別な分岐は不要。

5. **「MDN の『数値から長整数へ: ±Infinity なら false』は Infinity なら false ということ?」**
   → 誤読を訂正された。あれは「数値 vs BigInt」の組み合わせ専用のルール。本問題は BigInt / Symbol 考慮不要なのでその行ごと無視してよい。

6. **「Date は書籍のアルゴリズムに従わず、問答無用で valueOf() から始めてよい?」**
   → ダメ。テストの `date1 == date1.getTime()` (false) / `date1 == date1.toString()` (true) が valueOf 優先だと逆転する。eq では Date だけ toString 優先、他は valueOf 優先。一方 lte (関係演算子) は Date も含め常に数値優先でよい、と教わった。

### 実装方法の相談

7. **「順序を切り替えられる変換ヘルパーとはどういう意味?」**
   → valueOf→toString / toString→valueOf は「どちらを先に試すか」しか違わないので、順序をフラグ引数で受ければ 1 つの関数で済む、という骨組みのスケッチを得た (基本値判定と両方失敗時の扱いは自分で実装)。

8. **「どちらがオブジェクトか if で振り分けるのは面倒?」**
   → 両方オブジェクトのケースは「同じ型→===」で処理済みなので高々片方だけ。isObject ヘルパー切り出しと、再帰のおかげで各分岐が 1 行になることを教わった。

9. **「オブジェクトの場合、相手の型や Date かどうかで組み合わせ爆発しない?」**
   → 「変換するか (相手が数値/文字列のときだけ)」と「どう変換するか (自分が Date かどうかだけ)」は独立した 2 つの質問で、掛け算にならない。変換結果の型の分岐も再帰が吸収するので不要。

10. **「ステップ③ (数値 vs 文字列) の時点でどちらかがオブジェクトでは?」**
    → eq は呼び出しごとに毎回先頭からルールを見直す。③に来るのは両方基本値のときだけで、オブジェクトは⑤が拾って再帰で③に戻ってくる。`eq(new Test("1", {}), 1)` の 3 段トレースで理解した。

11. **「同じ型かどうかは typeof で測れる?」「基本値の typeof は?」**
    → 測れる。null vs オブジェクト・関数 vs オブジェクトの誤判定はどちらも結果が偶然一致するので無害。基本値の typeof 一覧 (null だけ "object" の罠) を確認した。

12. **「再帰のとき return は必要?」**
    → 必須。return しないと結果が捨てられ undefined が返る。6 ステップ全分岐が return で始まる。

13. **「Date 判定は簡単にできる? toString は直接 return でいい?」**
    → `instanceof Date` で判定。`!(a instanceof Date)` はカッコ必須 (`!a instanceof Date` は常に false になる罠)。toString の結果は基本値チェックが必要で、return すべきは「変換結果で再帰した結果」。

14. **「基本値にならない場合エラーで処理が止まらない?」「valueOf 自体がエラーを出すのでは?」**
    → 認識を訂正された。valueOf/toString 自体は何を返してもエラーを出さない。基本値チェックと TypeError の throw は == アルゴリズム側 (=自作ヘルパー) の仕事。本物の == も両方失敗時は TypeError で止まるので、throw するのが忠実な再現 (テストには該当ケースなし)。

15. **「toString は null や undefined に変換できて valueOf はダメとかある?」**
    → メソッド間の区別はなく、見るのは「返り値が基本値か」だけ。null/undefined は基本値なので valueOf が null を返したらそれを採用する (toString に進まない)。

### デバッグ

16. **「TypeError: Cannot convert undefined or null to object (valueOf(obj) の行)」**
    → `valueOf(obj)` ではなく `obj.valueOf()` とメソッドとして呼ぶ、という書き方の間違いを指摘された。エラーメッセージが妙な内容になる仕組み (Object.prototype.valueOf が this なしで呼ばれる) も教わった。

17. **「eq をテストしたら 4 つ落ちた。テストコードと実装を見て落ちそうな 4 つを挙げて」**
    → AI がコードとテストを机上トレースし、`typeof === "object"` だけの判定では関数 (typeof "function") が漏れて testFunc の 4 ケース (期待値 true) が false になること、加えて null が「Date でないオブジェクト」の条件に当てはまり `ValuePrimitive(null)` でクラッシュする 2 ケースを指摘された。修正 (isObject 条件への変更) は自分で行った。

18. **「function ってオブジェクト扱いなの?」**
    → 関数は「呼び出せるオブジェクト」(instanceof Object が true、プロパティを持てる)。testFunc が関数に toString/valueOf を生やせるのはこの性質のため。typeof だけが "function" と特別扱いする。

### lte の実装

19. **「lte も eq と同じように作れる? 数値優先でも数値に変換されないのが気になる」**
    → lte は「①両辺を無条件で基本値化 (Date 分岐不要・再帰不要) ②両方文字列なら文字列比較、それ以外は両方 Number() して比較」の一直線構造で eq より単純。「数値優先」は valueOf を先に試すだけで結果が文字列のこともある、という着眼が正しいと確認。書籍の「数値には変換されません」の一文は「基本値化の後に数値化までは行かない (文字列比較のチャンスを残すため)」の意味と教わった。

20. **「基本値に valueOf() を使うとエラーになるのでは?」**
    → ヘルパー先頭に「オブジェクトでなければそのまま返す」ガードを置けば valueOf に到達しない。なお基本値でエラーになるのは null/undefined だけ (他はラッパーオブジェクト経由で動く)。

21. **「a<b を return でいい? b<a とかもいるの?」**
    → `a <= b` は「a < b または a === b」なので `a < b || a === b` で書ける。NaN は両項とも false になるので特別扱い不要。比較式はそのまま return してよい。

22. **「lte(a,b) で a が小さい方と決めつけていいの?」**
    → lte = less than or equal で、テストコードの `a <= b` が仕様そのもの。eq と違い lte は引数を入れ替えると答えが変わるので、a 由来の値を必ず < の左に置く必要がある。

23. **「ガードは『object でも function でもない』でいける?」**
    → typeof null が "object" なので null がすり抜けてクラッシュする。`obj === null ||` を足す必要がある。既存の valueOf/toString 結果チェックの `n !== null &&` も向きが逆 (null は基本値扱いにすべき) と指摘を受けた。

24. **「lte で 2 つエラーになった。比べ方をミスった?」**
    → AI が机上トレースで `lte(10, new Test("10", null))` と `lte(10, testFunc("10", null))` の 2 件と特定。比較ロジックは正しく、原因は valueOf の結果チェックの `n !== null` (null を基本値として採用せず toString に進んでいた)。左側配置のケースは偶然同じ答えになるため右側配置だけ落ちる、という解説を得た。修正は自分で行った。

### リファクタ相談

25. **「eq で同じようなことを 2 回していて気持ち悪い」**
    → isObject/isPrimitive ヘルパーの切り出し、Date 判定を変換ヘルパー内へ移動 (4 行→2 行)、== の対称性を使った引数入れ替え再帰 (eq 限定、lte では不可) の 3 段階の案を得た。

26. **「ヘルパーにガードを入れると eq 側とチェックが二重にならない?」**
    → なるが許容してよい。eq 側は「ルールを適用すべきか」というアルゴリズム上の判断 (削ると eq(null,1) が無限ループ)、ヘルパー側は「何を渡されても安全」という部品の堅牢性で、答えている質問が違う。
